# ② 日志驱动的测试质量保障（工程笔记）

## 1. 为什么要自动化解析

人工翻 Log 的三个问题：

1. **规模**：老化测试一晚上万行，人眼必然漏看偶发 FAIL；
2. **转录错误**：把结论抄进报告时可能抄错数字、抄错版本；
3. **不可复算**：只有结论没有原始聚合过程，别人无法复核。

目标：**原始 Log 是唯一事实来源（single source of truth）**，报告由脚本一键生成，任何人拿到同一份 Log 都能算出同一份报告。

## 2. 好日志格式的设计原则

- 一行一个事件，固定时间戳开头 `[YYYY-MM-DD HH:MM:SS]`；
- 键值对用 `KEY=VALUE`，无空格，便于正则解析，也方便 grep；
- 必需字段齐全：`DUT` / `FW` / `TEST` / `RESULT`；
- FAIL 必须带**机器可读错误码**（`E_TIMEOUT` 而不是"好像超时了"）；
- 测量值带单位约定（误差统一毫米、RSSI 统一 dBm），在文档里冻结。

## 3. 解析器设计要点（对应 scripts/parse_test_log.py）

1. **容错但记账**：格式不符的行跳过并计数，不中断整批解析；
2. **按 DUT × 测试项聚合**：通过率、误差统计、信号质量、失败码直方图分桶；
3. **样本标准差用 n−1**：小样本下区分总体/样本口径；
4. **缺失即 null**：没有误差数据就不编 0；
5. **固件覆盖单独列出**：一个 DUT 出现多个 FW 版本时显眼提示混版本风险；
6. 纯标准库实现，测试机上无需 pip install，降低使用门槛。

## 4. 从统计结果怎么读问题

- **失败码集中在 E_TIMEOUT 且 RSSI 很低**：优先怀疑链路/距离/遮挡，而不是算法；
- **测距误差 σ 很大但均值正常**：重复性差，查多径/天线延迟标定/治具松动；
- **新版本通过率下降但样本很小**：不能下结论，扩大样本并记录置信限制；
- **只有一块 DUT 异常**：个体硬件问题；所有 DUT 在同一测试项异常：协议/固件/治具的系统性问题。

## 5. 下一步可扩展

- 多日志文件批量汇总 + 跨固件版本配对对比；
- 误差 / RSSI 分布图（matplotlib 可选依赖，不强加给只需要报告的用户）；
- CI 思路：Log 入库时自动跑解析 + 阈值规则（通过率低于门限即标红）；
- 与 ML 评测相通的习惯：原始数据与结论分离、版本指纹绑定、失败不删除——这和算法实验的可复现性是同一套纪律。

## 6. 自测题

1. 为什么报告不能让测试人员手填通过率？给出两个具体风险。
2. 一行 FAIL 没有错误码，解析器应该崩溃、跳过还是记 UNKNOWN？为什么？
3. 三份 Log 里 DUT=U001 的 FW 同时出现 1.2.2 和 1.2.3，你会怎么处理这批数据？
4. 若要增加"温循条件"维度，日志格式最小改动是什么？
